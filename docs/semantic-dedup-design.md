# 语义去重 + AI 分层判断（无人工）设计

状态：第 3 版（已按第 1、2 轮设计审查修订）。适用范围：新版日报 `brief.format = digest_v2`（生产现用）。旧版格式（legacy，L1/L2/L3 + 人工复核）不改动、不运行。Telegram 每日要点不在本次范围内。

## 1. 目标与已定产品规则

1. 同一件事被多个来源报道时合并为一条（合并"同一件事"，不合并"同一类"）。
2. 合并依据改为"AI 结构化摘要 → 向量 → 余弦相似度"，相似度很高且关键事实不冲突时直接合并。
3. AI 判断分两层（L1、L2），去掉 L3，不需要人工复核。
4. **未判定条目（L1、L2 都没给出有效结果）不发布、不丢弃：本期推迟发布，每 15 分钟重试一次；距计划发布时间超过 2 小时仍未解决，则停止本期调用、本期不发布，并在后台显示错误。**（用户 2026-11-05 决定）
5. **L1、L2 都以内容安全为由拒绝处理的条目按"排除"计入已判定，日志与后台列出。**（用户 2026-11-05 决定）
6. 后台新增向量模型设置（OpenAI 兼容 `/embeddings`）。

不变：采集层的条目身份键（`extractItemKey`）与内容指纹（`contentFingerprint`）。

## 2. 数据流（buildDigest 内）

```
loadItems(窗口) → isReplyOrTrivial 确定性过滤                           现有
→ L1 结构化摘要（缓存）→ 向量（缓存）
→ 分池聚类：链接线索 + 向量相似度 + 结构化冲突检查 + 灰区 L2 逐成员确认   结果 = 固定的事件组
→ 各版块按固定事件组生成，程序保证不跨组重组
→ 判定完整性检查：存在未判定条目 → 本期不落库，退出码 75（等待重试）
```

### 2.1 L1 结构化摘要

- 输入：标题 + 规范化正文（`coalesce(fulltext_text, clean_text)` 去噪后截断 1,500 字）。每批 20 条。
- 输出：`{ id, subject, action, object, version, numbers[], event_time, summary }`。`summary` ≤120 字，供向量与 L2 使用，不直接展示。
- 缓存表 `ai_item_notes`，键 `(input_sha256, task, config_id)`：
  - `input_sha256` = 实际送模型的规范化输入的哈希（全文抓取原地更新后会自动失效）；
  - `config_id` = 哈希(供应商, 去掉凭证的端点 origin+path, 模型, 提示词版本, 预处理版本)。
- 只缓存校验通过的模型结果；回退文本不写缓存。

### 2.2 向量

- 请求：`POST {base_url}/embeddings`，`{ model, input: string[], encoding_format: "float", dimensions? }`，每批 64 条，单条截断 2,000 字。
- 响应校验（任一不过则整批作废）：`data[].index` 完整、唯一、在范围内，按 index 重排；每条为非空数组、全部有限数值、范数 > 0；本次运行内维度锁定（首个有效批次确定，之后必须一致；配置了维度则必须等于配置值）；响应体大小上限 32 MB。
- 归一化后转 Float32，再次检查有限性。
- 缓存表 `embedding_cache`，键 `(text_sha256, config_id, req_dims)`，`req_dims` 非空整数（0 表示自动）；另存 `actual_dims`，BLOB 长度必须等于 `actual_dims × 4`，读取时再校验，不符的行视为不存在。
- `config_id` = 哈希(端点 origin+path, 模型, 请求维度)。换端点/模型/维度即换缓存空间。

### 2.3 分池聚类（得到固定事件组）

- 池：官方动态按厂商分池；时政一池；社区（LINUX DO / V2EX / 其他 context）一池。只在池内合并。
- 排序 `(coalesce(published_at, first_seen_at), id)`，结果可复现。
- 共享链接只是召回线索：两条共享某个具体链接（排除首页、厂商根域、仓库/文档根路径等泛链接）时，相似度门槛降到 `sim_low`，但仍走下面的冲突检查与完全链接；**不再用并查集直接合并**。
- 加入聚类的条件（完全链接：与组内**每个**成员都满足）：
  - 相似度 ≥ `sim_high`（默认 0.90）且结构化字段无冲突 → 直接加入；
  - 相似度在 `[sim_low, sim_high)`，或 ≥ `sim_high` 但存在冲突 → 灰区，交 L2；
  - 否则不加入。
- 自动合并除相似度外还要求事件身份兼容：`subject` 规范化后相同或一方包含另一方；`object` 不冲突；`event_time` 都有时相差不超过 48 小时。任一无法确认即进灰区。
- 结构化冲突（有冲突必进灰区）：双方都有 `version` 且不同；`action` 属于互斥对（发布/下线、故障/恢复、涨价/降价等，规则表在 rules.yaml）；同一指标的数字不同。
- L2 灰区确认：一次给 L2 "候选条目 + 组内全部成员（每条的结构化摘要和标题）"，问"候选与这些成员是否同一件事、是否有冲突事实"。只有 L2 明确"是"才加入。否决记为禁止合并关系，后续不再尝试把这两条放进同一组。
- 每期灰区确认上限 60 次，超出按"不同事件"处理（多一条重复，不丢内容）。
- 阈值与模型强相关，在后台与模型一起配置；`preview.ts` 输出每对合并/否决的分数，便于用最近数据校准。

### 2.4 各版块使用事件组

- **官方动态**：composeVendorEvents 改为"给定固定事件组，只为每组写标题和摘要、判断 trivial/repeat"。程序校验输出与输入组一一对应（缺、重、越界都算无效），不允许模型重新分组。
- **72h 重复判定**：历史事件用不可变记录中的"厂商 + 标题 + 摘要"生成向量；每个当前事件组分别检索最相似的 5 条历史事件，连同对应关系交给模型判断 repeat。向量检索失败时恢复原有"按厂商的历史标题"比较，不把"没取到向量"当成"没有历史"。
- **转载判定**：社区条目与 72h 官方条目相似度 ≥ `sim_low` 时，交模型判断"是否只是转述、没有官方之外的新信息（项目、经验、事实）"；只有明确"是"才排除，不确定则保留。
- **时政速览**：按事件组提交；每组提交全部成员的标题与摘要（每组总长度预算 600 字，超出时按成员均分截断），代表条目只用于排序和来源计数。现有的每来源 25 条上限改为按事件组计数。输出协议改为逐组 `{ group_id, selected, text }`，每个输入组必须有一条结果（ID 完整性校验），程序只用 `selected=true` 的组生成速览，一条速览只对应一个组。
- **技术干货 / 羊毛资讯**：同窗口内的交叉发布按事件组合并，替代二元组 0.6 阈值；与 72h 已推送内容的比较同样改为向量检索 + 模型确认，检索失败恢复现有标题相似度比较。

## 3. AI 分层（L1 / L2，无 L3、无人工）

- L1 = `providerFromEnv('L1')`；L2 = `providerFromEnv('L2')`（未单独配置时同 L1）。
- 所有按条判定（摘要、judgeTutorials、judgeDeals、转载、describeProjects、事件组文案）输出都做**完整性校验**：输入 ID 与输出 ID 一一对应，缺失、重复、未知 ID 都算无效。只把无效/缺失的条目送下一步，已通过的结果立即保留。
- 判定类 Schema 增加 `confidence`（0–1）。
- 升级到 L2：L1 最终失败；L1 结果缺失/无效；`confidence < 0.6`；灰区确认。
- 内容过滤：批次被过滤 → 拆成单条重试 → 单条仍被 L1 过滤则交 L2 → L2 也过滤：**视为已判定"排除"**（用户决定），记录原因（模型拒绝处理），日志与后台列出，不计入未判定。
- L2 名额：每期判定 80 条 + 灰区 60 次；超出部分保留 L1 结果（L1 也没有有效结果的条目计为未判定）。
- 预算归属"每期 + 每次触发来源"并持久化：表 `run_ai_budget(run_id, trigger, kind, used)`，每次实际 HTTP 派发前原子扣减（`UPDATE … SET used=used+1 WHERE used<cap`，含内部重试与拆批）。定时运行的多次尝试（含崩溃重启）共用一份预算；每次手动重跑另开一份（审计记录），不重置定时预算。
- 未判定条目 → 见第 5 节"推迟发布"。

## 4. 调用、重试与故障分类

统一由一个调度函数 `callTiered` 负责重试，取代 `digest/src/ai.ts` 中 `call()` 的"无差别调用两次"及各处拆批重试，避免叠加：

| 错误类型 | 同一层处理 | 之后 |
|---|---|---|
| 网络 / 超时 / 5xx | 退避重试 2 次（含在 withTransientRetry 内，不再外层叠加） | 升级 L2 |
| 429 限流 | 按结构化传递的 Retry-After 等待（上限 60 秒），最多 2 次 | 升级 L2 |
| Schema 不合格 / JSON 解析失败 | 重试 1 次 | 升级 L2 |
| 截断 | 提高输出上限或拆半批重试 1 次 | 升级 L2 |
| 400 输入过长 / 批量过大 | 拆半批重试 1 次 | 升级 L2 |
| 401 / 403 / 供应商初始化失败（缺密钥、缺 Base URL） | 不重试 | L2 与 L1 配置相同则跳过 L2；否则升级 L2 |
| 内容过滤 | 拆单条 | 见第 3 节 |

- 每期 AI 请求总数上限 600 次（含重试，按上面的持久化预算计），超出后剩余条目计为未判定。
- 请求期限覆盖连接、响应头和响应体读取（读取响应体期间计时器不取消）；单次请求 120 秒。
- 向量调用：临时故障 / 429 同上；400 仅在错误为输入长度或批量限制时拆分；401/403、404（错误路径）、模型不存在、维度不支持等配置错误 → 本期立即停止向量调用。
- **向量整体不可用**（后台未启用、配置校验失败、配置错误或故障）→ 只降级"合并"能力：仅合并规范化网址完全相同的条目，其余单独成组；不恢复并查集预合并和二元组阈值排除。分层判定与完整性门禁照常执行，不推迟发布，日志与后台显示警告。**部分条目缺向量** → 已验证的事件组保留，缺向量的条目单独成组（不错合、不丢弃）。
- 供应商创建移入 buildDigest 的调度层，创建失败按"401/403/初始化失败"处理，不再让整个 brief 进程在构建前崩溃。

## 5. 推迟发布与停止（用户规则）

采用"一个进程内循环"实现，不依赖 systemd 反复重启：

- 触发来源由入口显式传入：`brief-run.service` 传 `--trigger timer`，后台请求 worker（brief-requests）传 `--trigger manual`。本次尝试的来源单独记录在 `run_attempts(run_id, trigger, started_at, finished_at, outcome)`，不改写 `runs.trigger`。
- 定时运行：固定时刻表 = 窗口结束 + 15、30、…、120 分钟；绝对截止 `deadline` = 窗口结束 + 2 小时。
  1. 执行一次构建尝试。
  2. 无未判定条目 → 正常落库发布，结束。
  3. 有未判定 → 不落库；`runs.status='waiting_ai'`，记录未判定数、最后错误类型、`next_attempt_at`（下一个固定时刻）；进程睡眠到该时刻后重试，只补未完成部分（缓存命中其余）。
  4. `deadline` 到达：取消所有在途请求（AbortController 链接到截止时间）、不再派发；`runs.status='failed'`，`error` 写"AI 判定连续失败超过 2 小时，本期未发布：未判定 N 条，最后错误类型 X"；进程退出码 3。
- `brief-run.service`：`TimeoutStartSec=3h`（大于 2 小时截止 + 单轮最长时间）；`Restart=on-failure`、`RestartSec=5min` 保留作崩溃兜底；`RestartPreventExitStatus=3`。崩溃重启后读取 `runs.status/next_attempt_at/deadline`，已过截止则直接标记 failed 退出 3，未过则按时刻表继续；截止判断基于持久化的窗口结束时间，不依赖内存。
- `run.ts` 对 brief 子步骤的退出码 3 直接透传，不再经过通用 `markRun('partial')`，保留子步骤写入的状态与错误。
- 手动重跑（后台 `/runs/:id/rerun`）：不受截止限制，只执行一次构建尝试，不睡眠重试；仍有未判定则 `failed` 并更新错误信息，退出码 3。
- 修复现有缺陷：后台请求解析 `packages/web/src/requests.ts` 只接受 morning/noon/evening，拒绝当前的 `YYYY-MM-DD:daily`。改为用当前窗口配置与 `windowFromKey()` 校验，并补 daily 入队、取出、执行的回归测试。
- 运行互斥：定时、手动、直接 CLI 入口共用按 `run_id` 的租约表 `run_leases(run_id PRIMARY KEY, owner, expires_at)`：原子获取（不存在或已过期才可获取），每分钟续租，租期 5 分钟，结束释放。取得租约后重查"是否已有 final 简报"与截止状态；已发布则直接结束，不会被另一尝试改成 failed。发布事务内再次校验租约所有权。拿不到租约的尝试直接退出（定时运行退出码 0 并记录"另一尝试正在进行"）。
- 后台首页"待处理"区显示 `waiting_ai`（重试中：下次重试时间、未判定数、最后错误类型）、`failed`（本期未发布及原因）、以及本期"模型拒绝处理而排除"的条目数与标题。
- 已发布的简报不重写、不补发。

## 6. 缓存、并发与幂等

- 缓存表（迁移 018）：
  - `ai_item_notes(input_sha256, task, config_id, result_json, created_at, PRIMARY KEY(input_sha256, task, config_id))`：L1 摘要、各类判定、灰区确认（task 区分；灰区的 input 为"候选 + 全部成员"的规范化输入）。
  - `embedding_cache(text_sha256, config_id, req_dims, actual_dims, vector, created_at, PRIMARY KEY(text_sha256, config_id, req_dims))`。
  - 所有列 `NOT NULL`，`req_dims INTEGER NOT NULL CHECK(req_dims >= 0)`，`CHECK(length(vector) = actual_dims * 4)`。
- 写入：`INSERT … ON CONFLICT DO NOTHING` 后**重新读取**胜出行并使用它，保证同一键在各进程中结果一致。
- 进程内对同一键的并发请求合并为一次。
- 不承诺跨进程"只付费一次"：brief-run 与 preview 同时未命中时可能各请求一次；请求完成到写入缓存之间崩溃也会重新请求。只读 preview 未命中缓存时同样会付费（文档与 preview 输出中注明）。
- preview 以只读方式打开数据库：表存在则读缓存、不写；表不存在（未迁移）则不读缓存，并在输出中提示"缓存表缺失，请先运行迁移"。
- 保留期：brief-maintain 删除 30 天前的缓存行。

## 7. 配置与后台

- 新密钥 `EMBEDDING_API_KEY`（AES-GCM 保管库，只显示是否设置与掩码；审计只记名称和长度）。
- 新设置：`embeddingEnabled / embeddingBaseUrl / embeddingModel / embeddingDimensions / dedupSimHigh / dedupSimLow`。
- **单一配置解析函数** `resolveEmbeddingConfig()`：环境变量优先，其次保管库；页面显示、连通性测试、worker、preview 都用它，页面标出哪些字段被环境变量覆盖。环境变量同样经过校验。
- 校验：
  - Base URL：必须是 https；http 只允许 loopback（127.0.0.0/8、::1、localhost）；不允许 URL 中带用户信息（user:pass@）或查询参数；长度 ≤ 300。
  - 模型 ID：非空，≤ 200 字，无控制字符。
  - 维度：空（自动）或 1–8192 的整数。
  - 阈值：有限数，`0 < sim_low < sim_high ≤ 1`。
  - 启用开关：只接受 "on"/缺省。
- 两个开关含义分开：
  - `rules.yaml brief.semantic_dedup.enabled`：是否使用新流程（L1 结构化摘要、分层判定、完整性门禁、推迟发布）。关闭时行为与现状完全一致（测试验证调用次数与输出不变）。
  - 后台"向量模型"启用 + 配置校验通过：是否使用向量合并。新流程开启但向量不可用时，按第 4 节只降级合并能力，分层判定与门禁照常。
- 路由 `POST /settings/embedding`（保存）与 `POST /settings/embedding/test`（测试当前生效配置）：登录、CSRF、写权限；测试限 10 秒一次、同时最多 1 个、请求期限 15 秒。
- 设置页 L3 输入框标注"仅旧版格式使用"。

## 8. 密钥与错误信息安全

- 所有请求（补全、向量、连通性测试、重试）统一 `redirect: 'error'`。
- 传输层直接产出结构化错误 `{ kind, status, retryAfterSec?, code? }`，`code` 只取响应 JSON 中 `error.code`/`error.type` 且匹配 `^[a-z0-9_.-]{1,64}$`；**不保存原始响应体、请求头和异常对象**。日志、页面、审计、runs.error 只接收结构化错误。
- 现有 `retry.ts` 打印 `e.message` 的日志改为只打印 kind/status；现有适配器把响应正文放进错误信息的做法在本次涉及的调用路径中改为结构化错误（其他调用方保持兼容）。

## 10. 测试
