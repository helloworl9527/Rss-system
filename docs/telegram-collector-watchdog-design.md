# Telegram 采集器防卡死 + 汇总等补采完成 设计（第 2 版）

背景（2026-11-07 事故）：采集器进程存活但 reconcile 内某个 Telethon 请求在断线后永不返回，主循环与心跳一起停摆 10.5 小时；supervisor 只在子进程退出时重启。07:00 无总结任务，08:00 日报带「群组要点生成中」发布。11:58 手动重启后补采，12:07 汇总在超过 3 小时宽限后以不完整数据生成（窗口内 5,990 条中 1,043 条在其后才补进），之后不再重建。

第 1 版（单来源超时 + 进程内重连 + 事后重建汇总）经审查有多处漏洞，改为下面更简单的链路。

## 1. 采集卡死：外部看门狗兜底（进程外强制终止）

- Python worker 通过 supervisor 传入的管道（fd 3，环境变量 `TELEGRAM_PROGRESS_FD=3`）写入进度信号（单字节，非阻塞写，管道满或不存在时忽略）。写入点：
  - 主循环每轮开始与结束（含 5 分钟休眠前）；
  - 每保存一条补采消息（节流：同一秒最多一次）；
  - 每处理完一个来源（成功或出错）；保留期复查每批 `get_messages` 之后；补采中每张图片处理完之后。
- supervisor 用单调时钟记录最后一次收到进度的时间，每 30 秒检查：超过 20 分钟没有进度 → 记录日志，SIGTERM 子进程，30 秒后仍未退出则 SIGKILL；子进程退出后 supervisor 以退出码 1 结束，由 systemd `Restart=on-failure`（10 秒）重启。
- 启动阶段（`connect()` 等）同样受看门狗约束：从子进程启动开始计时。
- 信号路径重写：systemd 停止服务（supervisor 收到 SIGTERM/SIGINT）时转发给子进程并在其退出后以 0 结束；除此之外子进程任何方式退出（非零码、被信号杀死、看门狗终止）supervisor 都以 1 结束。不再「以同一信号自杀」（自身注册了处理器时无效，且 systemd 把 SIGTERM 视为正常退出不重启）。退出时清理定时器。
- 看门狗不依赖 SQLite，数据库忙或损坏不会让它失效；SQLite 心跳仍只用于后台展示。
- 不做进程内重连、不加单来源超时：任何位置卡住（RPC、取消清理、阻塞的同步调用）都由进程外终止统一处理。

## 2. 首次同步被中断不漏采（修复原有缺陷）

- 首次同步（`last_message_id = 0`）按时间倒序读取，若逐条推进游标，中断后下一轮会从已存最大 ID 正序续读，较早消息永久漏采。看门狗终止会让这种中断更常见。
- 改为：首次同步期间保存消息不推进游标；整轮完成后一次性把游标设为本轮见到的最大 ID。中断后下一轮重新做首次同步（已存消息按现有冲突更新去重）。
- 增量补采（`last_message_id > 0`，正序读取）保持逐条推进，可安全断点续补。

## 3. 汇总等补采完成再生成

`windowReady` 现行规则：存在未结束的单群任务时等待 40 分钟；超过时段结束 3 小时后不再等落后来源，直接生成。改为：

- 落后来源 = 启用、active、normal，且 `last_window_end < 时段结束` 的来源。
- 无落后来源 → 就绪（不变）。
- 3 小时内有落后来源 → 等待（不变）。
- 超过 3 小时：只跳过「在时段结束之后已被处理过但仍落后」的来源（`telegram_sources.updated_at > 时段结束`，即该轮同步出错，属于来源自身故障）；只要还有落后来源在时段结束之后**从未被处理过**（采集器停摆或补采还没轮到它），就继续等待。
- 超过时段结束 24 小时 → 无论如何生成（兜底，避免采集器长期停摆时永不出汇总）。
- 不做事后重建：避免重复扣费与覆盖较完整结果的问题。代价：采集器停摆期间汇总会推迟到补采完成后才出（今天的情况会在约 12:55 生成完整汇总，而不是 12:07 生成缺 17% 的汇总）。08:00 日报的行为不变（等待 5 分钟，未就绪则注明生成中）。

## 4. 不做

- 不加主动提醒（用户要求暂缓）。
- 实时事件中的图片下载无超时、过期任务重领等原有问题不在本次范围，记为后续。
- 不自动加群、不改已停用来源。

## 5. 测试

- Python：首次同步中断后不推进游标、完成后才设游标；增量同步逐条推进；进度信号在补采与每轮写入，fd 不存在时不报错。
- Node supervisor：无进度超过阈值时终止子进程并以 1 退出；有进度时不触发；systemd 停止时以 0 退出；子进程异常退出以 1 退出。阈值通过环境变量缩短后做真实子进程测试。
- 汇总就绪：3 小时内等待；超过 3 小时，落后来源未在时段后处理过 → 等待；落后来源在时段后已处理（出错）→ 就绪；超过 24 小时 → 就绪；无落后来源 → 就绪。

## 6. 第 3 版修订（按第 2 轮设计审查）

- **专用的同步尝试记录**（Telegram 迁移 006）：`telegram_sync_state` 新增 `last_attempt_at / last_attempt_ok`。每个来源每轮同步结束（成功、出错、本轮解析不到实体）都写入。汇总超过 3 小时宽限后，只跳过「时段结束后明确完成了一次失败尝试」的落后来源；`telegram_sources.updated_at` 会被改名、启停、重置令牌等操作更新，不再使用。
- **覆盖水位**：新增 `covered_until`，取最近一次**成功**的连续历史扫描的开始时刻，只在扫描成功结束后写入。`ensureDueJobs` 按它推进窗口（迁移前的旧数据退回 `last_success_at`）。扫描期间才到达、没被读到的消息不会让窗口被误判为完整。同步成功但水位尚未越过时段的来源继续等待。
- **复查不推进游标**：保留期复查读的是库里已有的 ID，不是连续历史，改为 `advance_cursor=False`。游标只由连续历史遍历推进；首次同步在遍历成功结束后一次性提交。
- **进度写入点补全**：复查中每条消息；补采路径的图片下载过程中（Telethon `progress_callback`）。实时事件路径的图片下载不报告进度，避免实时活动掩盖补采卡死。
- **supervisor 停止路径**：主动停止与看门狗共用终止函数，都在宽限期后 SIGKILL 兜底；退出码优先按「是否收到停止请求」决定（收到 → 0）。
- **已知限制**：24 小时兜底只对已有单群总结的时段生效（`runDueDigests` 从总结表枚举时段），采集器停摆整个时段且没有任何总结时，汇总在采集恢复后才会生成。`reload` 内单次 `get_entity` / 对话枚举没有中间进度，单次调用超过 20 分钟会被看门狗重启（视为卡死，符合预期）。

## 7. 2026-11-08 调整：覆盖水位不再等复查

- 现象：大群（保留期内 3 万条）每轮全量复查约 60 次 `get_messages`，一轮一个多小时；覆盖水位等复查结束才发布，Telegram 总结 08:28 才完成，08:00 日报再次显示「生成中」。
- 调整一：连续历史扫描成功后立即发布 `covered_until`（仍取本轮扫描开始时刻）。复查只负责同步之后的编辑，不再挡住总结；代价是总结生成后才被编辑的消息在汇总里是编辑前的版本（与原 3 小时宽限时一致）。
- 调整二：保留期复查每轮只查最近 24 小时，全量复查每 24 小时一次（单调时钟，进程重启后第一轮做一次全量）。消息永久保留时删除本就不同步，全量复查主要用于同步编辑。
